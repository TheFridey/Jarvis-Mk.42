fix(harness): stop the browser acceptance run from contaminating the owner's desktop export

The owner's live Presence on 4300 was authenticating against http://127.0.0.1:57533 - an ephemeral
port baked into the real apps/desktop/out by my browser acceptance run, with a synthetic bootstrap
credential. jarvis-up.ps1 reuses that export unless -Build is passed or index.html is missing, so the
test build became the application. That is a genuine defect and mine.

Isolation now:
- the owner's export is moved aside to apps/desktop/out.owner-backup before the build, and restored
  immediately after it; the run refuses to start if a backup is already present from a crash;
- the test build is relocated to .logs/browser-acceptance/export with a .acceptance-build marker and
  is what gets served, via a new JARVIS_EXPORT_DIR variable in serve-export.mjs;
- the launcher refuses to serve a directory carrying that marker: it deletes the directory and
  rebuilds, so a test configuration cannot survive into the application;
- cleanup runs in finally, so a thrown exception or failed startup still restores the owner build.

Regression evidence, asserted inside the journey itself rather than by inspection: the owner export
hash is identical before and after the build, identical again after the whole run
(bb2b9fbe...c33c), and no acceptance marker is left where the launcher looks. Three source-level
tests in launcher-hygiene.test.ts pin the invariant.

Browser journey: 18/18, exit 0, including the three isolation checks.

The already-contaminated build has been quarantined to .logs/browser-acceptance/ and apps/desktop/out
is absent, so the launcher rebuilds rather than serving it. The owner still needs `jarvis-up.ps1
-Build` once, or simply a normal start, which now builds because the export is missing.

Verification: 882 passed, 4 skipped (886), 145 files, vitest exit 0; typecheck, lint and fitness
clean.
